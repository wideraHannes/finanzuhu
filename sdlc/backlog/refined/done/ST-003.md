# ST-003: Manage transactions

**Source:** [`unrefined/ST-003.md`](../../unrefined/done/ST-003.md)
**Status:** refined

**As a** user of Finanzuhu
**I want to** add, remove, and reset transactions
**so that** my transaction list stays up to date while I can restore the demo's default data.

## Business context

The transaction ledger is currently the committed CSV file
`data/transactions.csv`, read through the cached `getTransactions()` function
in `src/lib/transactions.ts` and exposed read-only by
`src/app/api/transactions/route.ts`. The transaction page can filter and sort
these entries but cannot change them. Its dashboard summaries, budgets, and
assistant transaction tools all use the same ledger, so saved changes must be
visible wherever transactions are read.

The application is a demo with seed data. A separate, committed backup of that
original ledger and a user-visible reset allow experimentation without losing
the default data permanently.

## Scope decisions taken during refinement

- Additions, deletions, and resets persist in the CSV-backed ledger and remain
  after reloads and server restarts.
- The add form captures every current transaction field: date, signed amount,
  description, counterparty, category, type, payment method, and recurring
  flag.
- The user supplies a signed amount and explicitly selects the type.
- Removing a transaction deletes it immediately; there is no deletion
  confirmation or undo.
- The default ledger is kept as a separate committed backup file. The
  transaction page provides a reset action that restores this backup only after
  user confirmation.

## Acceptance criteria

1. The transactions page provides an add-transaction form containing inputs
   for date, signed amount, description, counterparty, category, type, payment
   method, and recurring status.
2. Submitting valid form data adds a transaction to the persisted ledger. The
   added entry appears in the transaction list without a full page reload and
   remains present after a reload or server restart.
3. The persisted entry has a unique ID and conforms to the existing
   `Transaction` shape.
4. Each displayed transaction has a remove action. Activating it immediately
   removes that transaction from the persisted ledger, the list, and any
   subsequent page reload.
5. The page provides a reset action. Before it restores data, it clearly warns
   that all additions and removals will be lost and requires explicit user
   confirmation.
6. After confirmed reset, the persisted ledger exactly matches the committed
   default backup. The list updates without a full page reload.
7. The existing dashboard, budgets, transaction API, and assistant tools read
   the updated ledger after an add, removal, or reset; they do not retain stale
   transaction data.
8. Client and server validation reject missing fields, malformed dates,
   non-finite amounts, invalid type values, and values that cannot be persisted
   safely. Validation failures show a readable error and do not change the
   ledger.
9. Write failures (for example, an unavailable or unwritable data file) show a
   readable error and leave the displayed and persisted ledger unchanged.
10. Unit tests cover creating a valid transaction, rejecting invalid input,
    removing an entry, handling an unknown ID, and restoring the default backup.

## Not part of this story

- Editing an existing transaction
- Undoing a deletion
- Importing or exporting transactions
- User accounts, authorisation, or per-user ledgers
- Concurrency handling for multiple users or simultaneous writes
- Version history beyond the single default backup
- Automatically categorising transactions
- Changing budgets when categories are added or removed

## Dependencies

- The current CSV ledger at `data/transactions.csv` and its transaction readers.
- A writable runtime filesystem. Deployments with a read-only or ephemeral
  filesystem cannot retain changes without additional storage, which is outside
  this story.

## Open questions

- Should the UI restrict the category and payment-method inputs to values
  already present in the ledger, or allow free text for new values?
- What validation should enforce consistency between signed amount and selected
  type (for example, must an expense always be negative)?
- Should a reset success message be shown after the default data is restored?
