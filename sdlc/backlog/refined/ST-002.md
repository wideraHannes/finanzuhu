# ST-002: LLM assistant for transactions and general questions

**Source:** [`unrefined/ST-002.md`](../unrefined/ST-002.md) — raised by Johannes Widera
**Status:** refined

**As a** user of Finanzuhu
**I want to** ask an AI assistant questions in plain language — about my
transactions as well as general knowledge questions —
**so that** I get answers without filtering and adding up bookings myself.

## Business context

Today the app answers fixed questions: the dashboard shows summaries and
budgets, `/transactions` offers search and filters (`src/app/api/transactions/route.ts`).
Anything beyond that ("How much did I spend on mobility in August?", "What is
a direct debit?") needs manual work or leaves the app. An assistant covers both
kinds of question in one place.

The ledger is the committed simulation in `data/transactions.csv`, read via
`getTransactions()` in `src/lib/transactions.ts`. The dashboard treats the
last booking (`referenceDate()`) as "today"; the assistant instead uses the
real current date, and knows the ledger ends at the last booking.

"World knowledge" means the model's own trained knowledge. There is no web
search.

## Scope decisions taken during refinement

- The assistant lives on its **own page `/assistant`**, with a new entry in
  the sidebar next to "Overview" and "Transactions".
- The model gets transaction data through **tool calls**, not by putting the
  whole ledger into the prompt.
- The conversation is a **chat held in browser state**: several turns per
  session, lost on reload, nothing persisted on the server.
- The LLM is called through the **Requesty gateway**, using the existing
  `REQUESTY_API_KEY` and `REQUESTY_BASE_URL` from `.env`.

## Acceptance criteria

1. The sidebar has an "Assistant" entry that links to `/assistant`.
2. `/assistant` shows a message list and an input field. The user can send a
   question and sees their message and the assistant's answer in the list.
3. Follow-up questions work within the session: the full chat history is sent
   with every request. After a page reload the chat is empty.
4. A new API route (e.g. `POST /api/assistant`) receives the chat history,
   calls the LLM through Requesty and returns the answer. The API key is read
   on the server only and never reaches the browser.
5. The LLM can call at least one tool that returns transactions from the
   ledger, filtered by date range and/or category. The tool is backed by a
   pure function in `src/lib/` that reuses `getTransactions()`.
6. The system prompt tells the model the real current date, so that
   "last month" or "this month" work, and the date of the last booking.
7. Questions about the ledger are answered with data from the tools, not
   made up. Example that must work: "How much did I spend on <category> in
   <month>?" gives the same total as the transactions page filtered the same
   way.
8. General knowledge questions (e.g. "What is a standing order?") get an answer
   without calling a tool.
9. While a request is running, the UI shows a loading state and the send
   button is disabled.
10. Errors are handled deliberately: a missing API key, an unreachable gateway
    or an LLM error lead to a readable error message in the chat, not a broken
    page. The request body is validated (empty message, wrong shape → 400).
11. Unit tests in `tests/unit/` cover the pure tool function(s): filter by date
    range, filter by category, both combined, no matches.

## Not part of this story

- Persisting chats (server or `localStorage`), chat history across sessions,
  multiple chats
- Streaming answers token by token
- Web search or other external data sources
- Tools that change data (creating, editing, deleting transactions or budgets)
- Access to budgets or account data via tools (only transactions for now)
- Assistant on other pages (floating panel, dashboard widget)
- Authentication, rate limiting, cost tracking
- Automated tests against the real LLM

## Dependencies

- **Requesty gateway** must be reachable with the key in `.env`. For
  development and review the `.env` must be present locally; it is not
  committed.
- A client library for the LLM call (e.g. an OpenAI-compatible SDK, since
  Requesty exposes an OpenAI-compatible API) or plain `fetch` — to be decided
  in the implementation plan.

## Open questions

- **Which model** is used via Requesty? Assumption: configurable through an
  environment variable (e.g. `REQUESTY_MODEL`) with a sensible default.
- **Which tools exactly?** Assumption: one `search_transactions` tool (date
  range, category, optional text) is enough; totals are computed either by the
  model or by a second small tool. To be settled in the plan.
- Should answers be in **German or English**? Assumption: the assistant answers
  in the language of the question.
- Should the assistant **refuse off-topic requests** (anything neither finance
  nor general knowledge), or answer everything the model allows?
- How should **amounts be formatted** in answers — same format as the app
  (`src/lib/format.ts`)?
- Is a short **disclaimer** needed ("AI answers can be wrong, no financial
  advice")?
