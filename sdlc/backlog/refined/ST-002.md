# ST-002: Multi language

**Source:** [`unrefined/ST-002.md`](../unrefined/ST-002.md) — raised by Gabriel
**Status:** refined

**As a** user of Finanzuhu
**I want to** use the app in German or English,
**so that** I can read the interface and my bookings in the language I think in.

## Business context

Every visible string is currently hard-coded in the components, while numbers and
dates are already formatted as German through fixed `de-DE` formatters in
`src/lib/format.ts` — the app is half-localised and consistent in neither
direction. The seed data in `data/transactions.csv` is English (`Rent July`,
`Groceries`), so a German user today reads a German interface shell around
English bookings.

## Scope decisions taken during refinement

- **next-intl with locale routing**: the locale becomes part of the URL
  (`/de/...`, `/en/...`). All existing routes move under a `[locale]` segment.
- **Everything is translated**, including category names and the booking texts
  (`description`, `counterparty`) from the data files.

## Acceptance criteria

### Infrastructure
1. `de` and `en` are supported; `de` is the default. No other locales.
2. All routes live under a locale segment: `/de`, `/en`, `/de/transactions`,
   `/en/transactions`. A request to `/` redirects to the resolved locale.
3. Resolution order on first visit: locale in the URL → stored choice →
   `Accept-Language` → default `de`.
4. A language switch in the header changes the locale, keeps the user on the
   same page, and persists the choice across reloads.
5. An unknown locale in the URL (`/fr/...`) yields a 404 rather than a crash.

### Texts
6. No user-visible string is hard-coded in a component any more; all come from
   message files, one per locale.
7. Both message files carry the same set of keys — a missing key is a build or
   test failure, not a silent fallback.

### Formats
8. Amounts, dates and numbers follow the active locale: `de` keeps today's
   format (`1.234,56 €`, `25. Sep. 2026`), `en` uses the English equivalent.
   The euro stays the currency in both.
9. The formatters in `src/lib/format.ts` take the locale instead of hard-coding
   `de-DE`; they stay pure and remain unit-testable.

### Data
10. Category names are translated: the category from the CSV is the stable key,
    the display name comes from the message files. Every category present in
    `data/transactions.csv` has an entry in both locales.
11. Booking texts (`description`, `counterparty`) are translated: the data files
    carry a language-independent key or per-locale text, and the transaction
    table shows the text of the active locale.
12. Category keys are never displayed raw — a category without a translation
    falls back visibly (key in brackets), so gaps show up in review.
13. Domain logic in `src/lib/` continues to work on the keys, not the display
    names: sorting, grouping and totals are identical in both locales.

### Tests
14. Unit tests in `tests/unit/` cover the locale-aware formatters and the key
    completeness of the message files.

## Not part of this story

- Any locale beyond `de` and `en`
- Right-to-left layouts
- Translated URLs (`/de/umsaetze` stays `/de/transactions`)
- Per-user profiles — the choice lives in the browser
- Translating the repository documentation (`README.md`, `sdlc/`)
- Locale-dependent currencies or exchange rates

## Dependencies

- None blocking, but it touches every existing component.
- Overlaps with **ST-001**: the budget view shows category names and amounts.
  Whichever ships second has to follow the convention of the first. Recommended
  order: ST-001 first, so ST-002 sweeps the strings once.

## Open questions

- **Size.** Criteria 11 and 12 (translating the booking texts) turn this into a
  data change on top of a UI change: `data/transactions.csv` needs a second
  text column or a companion file, plus the type in `src/lib/finance.ts` and the
  transactions API. Recommendation: split criteria 11 into its own story and
  ship infrastructure, UI texts, formats and category names first. Explicitly
  kept in scope per product decision — the split is a proposal, not a decision.
- Which shape do the translated booking texts take — an extra CSV column
  (`description_de`), or a key per booking with the text in the message files?
- Should `counterparty` really be translated? Company names such as
  "Hamburger Sparkasse" are proper nouns and normally stay untouched.
- Where exactly does the language switch sit in the header — next to the existing
  theme toggle?
- Is the stored locale a cookie (server-readable, works with locale routing) or
  `localStorage`?
